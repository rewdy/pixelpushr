# Operating pixelpushr

## Local browser-window walkthrough

Install Bun 1.3+ and Docker, then follow the [local development commands](../README.md). Copy `apps/api/.env.example` to `apps/api/.env`, run the database migration and Floci bucket initialization, and start `bun run dev`. Open `http://127.0.0.1:5173` in a desktop browser. Register the first account (email confirmation is required with Cognito, but not local auth), then create the single organization. This first account becomes the owner. The timezone selector starts with the browser's zone; search by city, IANA identifier, or UTC offset and choose a result. The displayed **Current UTC offset** can change with daylight saving time, so use the zone identifier—not today's offset—when planning future schedules. The owner can change the zone later in **Workspace settings**; other administrators can view it but not edit it. The selected zone affects schedules only after **Create workspace** or **Save changes**. Open **People & access** to invite another administrator; in local development, retrieve the invitation in Mailpit at `http://127.0.0.1:8025`.

On **Media**, select several images and videos with **Upload media**, or drop files anywhere on the Media page. The upload queue shows each file as queued, uploading, ready, or failed, with a reason for failures. Up to two files upload at once; a failed or unsupported file does not stop the others. These are status labels, not byte-level progress. The status list is page-local and clears when you leave Media; completed assets remain in the library. Then create or open a playlist on **Playlists**. Choose **Add media** to open the searchable thumbnail panel (a drawer on smaller screens); each **+** appends a new draft item, including when that asset is already in the playlist. Use item checkboxes to delete several items or apply one duration to selected images and repeat-for-duration videos; **Deselect all** clears the checkboxes without changing the draft. Play-once videos are not changed by bulk duration. Images use a duration; videos can play once or repeat for a duration. Reorder with the arrow buttons. All these edits remain local until **Save playlist**. **Show preview** plays the current unsaved draft in a compact loop; it is not a synchronized view of any running display and does not publish edits.

Reusable tags are case-insensitive; both the library and **Add media** picker match any selected tag, narrowed further by name search. Replacing a ready image or video accepts only the same kind, publishes after validation, and keeps its name, tags, playlist uses, order, and timing. A failed replacement leaves the current file playable. A replacement video remains ready if its still-frame poster cannot be created. Before deleting media used by saved playlists, the confirmation lists each affected playlist and item count. Confirming removes those item instances permanently; it does not unassign playlists from displays. If uses change while the dialog is open, deletion stops and the dialog refreshes for another review.

In the Media library, click an asset name or its **Edit** row action to open the side drawer. Save its name or tags there, or replace a ready file with one of the same kind. **Delete** remains in the row and opens the single-asset impact review. Select individual row checkboxes or **Select all visible** to work with the current filtered listing; changing the search or tag filter clears the selection. At most 100 assets can be selected in one operation. **Add tags** adds each entered tag to every selected asset while retaining each asset's existing tags. For example, adding “Campaign” to an asset tagged “Summer” and another tagged “Weekly” leaves them tagged “Summer, Campaign” and “Weekly, Campaign,” respectively. A tag limit or inaccessible asset rejects the entire batch.

**Delete selected** opens one review naming every selected asset and the saved playlist item count for each affected playlist. Confirming removes all selected assets and only their saved playlist item instances in one transaction; unrelated items retain their position and display assignments stay in place. If an asset or saved use changes after the review, deletion stops and refreshes the impact for another confirmation. Every deleted published file and poster remains available for the seven-day player handoff described below.

The Media, Playlists, and Displays administration lists show 25 records per page. Their authenticated API routes (`GET /admin/media`, `GET /admin/playlists`, and `GET /admin/displays`) accept optional `page` and `pageSize` query parameters. Either parameter opts in to paging: `page` defaults to 1, `pageSize` defaults to 25 and is capped at 100. Both must be positive whole numbers. For example, `GET /admin/media?page=2&pageSize=25&search=Lobby` returns `{ "assets": [...], "page": 2, "pageSize": 25, "total": N }`, with `total` counting all organization assets whose names contain “Lobby” before paging. `tags=ID1,ID2` matches either tag and combines with name search. Playlist and display responses use `playlists` and `displays` instead of `assets` with the same paging metadata. Requests without `page` or `pageSize` continue to return the complete array without paging metadata for editor and Overview consumers.

Register a display on **Displays**, open **Assign playlists**, then choose **Add playlist**. In the drawer, select a playlist and **Always-on** to append it after existing always-on playlists. For a timed assignment, choose **Scheduled**, then **Append** to add it to the normal queue with a start, end, and optional daily, weekly, or monthly repeat, or **Override** to displace normal playback with a start or **Activate now**, explicit expiration, and priority. Times use the workspace timezone. Missing or invalid windows are shown in the drawer. The display page lists every assignment with its mode and timing; use the remove action on its row, or reorder always-on rows and save their order. **Preview effective queue** checks a chosen local time without publishing anything. Copy the public player URL and open it in a separate browser window. The player needs no sign-in and starts automatically. Use `d` on the player keyboard to reveal a minimal online/offline diagnostic badge. A heartbeat updates the display's last-seen timestamp in the console.

**Overview** shows a **Simulated preview** for each registered display. It loops the currently resolved public manifest locally, using still frames for videos to limit playback work; it is not synchronized with the physical player and never sends a heartbeat. Cards refresh while visible about every 30 seconds and at known override transition times, then pause offscreen or when the tab is hidden. An empty or unavailable preview does not mean the device is offline. **Device last seen** and **Device-reported health** below each preview come from actual player heartbeats and are separate from simulation activity. Use **Manage display** to change assignments. Scheduling and overrides are managed per display, not from separate sidebar pages.

## Scheduling and override semantics

Always-active playlists appear first in the normal queue, in their configured order. All currently active additive schedules follow in schedule position order. Their items cycle as one combined queue. Normal manifest changes wait until the existing queue finishes; an empty player starts a newly assigned queue immediately. The player polls every 15 seconds by default. A new schedule may therefore be observed up to one polling interval after its boundary, then begins at queue rollover.

Schedule entry uses local date and time in the organization's IANA timezone. One-time windows include their start and exclude their end. In **Add playlist**, choose Scheduled, then Append or Override, and select **Repeat**: one-time, daily, weekly, or monthly. Set the repeat interval; weekly schedules require one or more weekdays, while monthly schedules use either a numbered date (1–31) or an ordinal weekday (first through fifth, or last). Months missing a numbered date, such as February 31, are skipped; a fifth weekday is skipped when absent. Optionally set a **Last occurrence date**, inclusive of starts on that date even if their window ends later. For three campaigns that rotate one per week, make three seven-day windows starting on consecutive weeks, each repeating every 3 weeks. The first always-on branding playlist remains active alongside each campaign. The **Preview effective queue** control shows the normal queue or winning Override for a chosen local time. Use **Edit** on an assigned Append or Override playlist to change its window, recurrence, or Override priority without changing its playlist or mode. The form uses the assignment's saved timezone even if the organization setting has since changed; fields you leave untouched retain their exact saved values, including seconds from **Activate now**. **Save settings** is disabled when nothing has changed, and **Cancel** makes no write. If another administrator changes the assignment first, the save reports a conflict; close the form, reload the assignment, review the latest values, and retry. After a successful edit, the assignment summary and schedule preview refresh, and returning to **Overview** fetches the latest simulation. Changing the organization timezone preserves each recurring window's entered wall-clock date/time in the new zone; one-time windows remain fixed absolute instants. Ambiguous fall-back times use Temporal's default earlier-offset interpretation, and nonexistent spring-forward times shift forward.

An override has an explicit start, expiration, and priority. Repeating Overrides require a first start/end and cannot use **Activate now**; selecting a repeat disables that option. While active, only the highest-priority override playlist plays; ties resolve deterministically by assignment ID. Start, end, and winner changes interrupt the current item immediately. **Activate now** is one-time only: it uses the server's current time as the start but still requires an explicit expiration. The next player manifest activates it. The manifest carries absolute transitions and server time so the browser can compensate for clock drift. Clock synchronization on the player device is still recommended. The player receives a rolling 14-day set of future Override windows plus any currently active window's full known end. Offline, it honors only the fetched occurrences; later repeats require an online refresh. A long cached Override still ends at its known time even when the device is offline.

Within a stable normal or override queue, the public player crossfades to the next item over the final 500 ms of an image or repeat-for-duration video's configured time. This overlap counts within that duration, so a 10-second item still advances at 10 seconds; repeat-video loops inside its duration do not trigger a fade. A play-once video fades during its final 500 ms when its remaining time is known. If duration is unavailable or the next asset cannot be prepared, the player makes a direct cut or skips the unavailable item rather than extending playback or leaving a stale overlay. Override start, expiration, and winner changes never fade: they cut at the server-adjusted effective time, including during an item fade or while offline with a cached override window.

## Media and offline behavior

Accepted MIME types are JPEG, PNG, WebP, GIF, MP4, and WebM. The API checks file signatures, upload size, and basic browser preview metadata before publishing. It does not transcode or deeply inspect video codecs. An H.264 MP4 fixture is covered by the Chromium browser tests; audio codecs have not been validated, and the player is muted. Verify other codecs on the actual playback browser and hardware. GIFs display as the browser animates them and advance at the configured image duration. Defaults are 20 MB per image and 500 MB per video, configurable through API environment variables.

After a video becomes ready, the browser attempts to capture an early frame and upload a JPEG poster through the authenticated API. The poster is limited to 1 MB. If extraction or upload fails, the video stays ready and the media library and playlist editor show a video fallback icon; older videos without posters behave the same way. To retry with the current UI, upload the video again. The API also accepts a JPEG poster for an existing ready video at `PUT /admin/media/:id/thumbnail` for a future dedicated retry control; pass the current asset's `contentVersion` as the `x-media-version` header so a late poster cannot attach to a replacement. Local development stores posters in Floci beside the original video (or in `.local-media` with local storage); Mailpit is only for invitation email. To check the full local path, start Compose and `storage:init` as in the README, upload a playable MP4, and confirm its still image appears in the Media library. A failed poster should not prevent adding that video to a playlist.

The reference player is a current desktop Chromium browser, tested with Playwright in a separate browser window. The Raspberry Pi Zero W is a future hardware target, not yet performance- or codec-validated. The player keeps the last valid manifest in local storage and prefetches normal and override media into browser Cache Storage. A failed refresh leaves current playback running; on reload during an outage, cached media can play if the browser retained it. Known override expiration still returns to the cached normal queue offline. Browser storage is best-effort and may be evicted; do not treat it as durable emergency delivery. Each item with an advertised `Content-Length` above 500 MB is skipped by the prefetcher. For deployments, test the actual kiosk browser's cache quota, autoplay behavior, network recovery, and sleep settings.

When media is replaced or deleted, the old published object and poster remain available for seven days so recently issued player manifests can finish their normal queue handoff. This is not indefinite offline retention. A replacement first uploads to a temporary key; the server validates and copies it to a separate, non-writable public key before publication, so reusing the original upload URL cannot change what players see. The scheduled AWS media-cleanup Lambda runs daily; locally, run `bun run --filter '@pixelpushr/api' media:cleanup` with the same API environment settings. Cleanup expires abandoned and successful temporary uploads and failed final copies after one day. Run it again after a failure; it is safe to retry. The versioned S3 media bucket expires noncurrent versions eight days after they become noncurrent, so underlying versions do not accumulate indefinitely after a key is retired.

## AWS deployment

The Terraform root is `tf/`, with infrastructure in `tf/modules/platform/`. It creates two private and two public subnets across two availability zones, a single NAT gateway, private RDS PostgreSQL with an RDS-managed master secret, an HTTP API backed by Hono Lambda, S3 buckets for the SPA and media, one CloudFront distribution routing `/api/*` and `/media/*`, a Cognito user pool, SES sender identity, and CloudWatch log groups. Private Lambda access to Cognito, SES, S3, Secrets Manager, and public key discovery goes through NAT. A single NAT is economical for the MVP but is not highly available across availability zones. RDS and the NAT gateway incur ongoing charges even when idle.

Production configuration lives in [tf/main.tf](../tf/main.tf). The site is `https://pixelpushr.app` in `us-east-1`, with `invites@pixelpushr.app` as the invitation sender. The domain must already delegate to its public Route 53 zone. Terraform requests the ACM certificate in **us-east-1**, creates the DNS validation record in that zone, and waits up to 30 minutes during apply for ACM to issue it before creating CloudFront.

Terraform creates an SES domain identity and publishes its three Easy DKIM CNAME records in Route 53. In SES in **us-east-1**, confirm the domain is verified and DKIM is successful before testing invitations. Request transactional production access in that region so SES can deliver to unverified recipients. AWS reviews that request separately from Terraform. The From address can send through the verified domain without an inbox.

Set `initial_owner_email` in [tf/main.tf](../tf/main.tf) to the mailbox that should claim a new workspace. Register with that address, complete Cognito email confirmation, sign in, and select **Create workspace**. The API checks the signed-in account's current verified email before granting ownership. Changing this setting after setup does not transfer ownership.

The backend in [tf/versions.tf](../tf/versions.tf) stores state at `s3://drewmey--devops-tf-state/pixelpushr/production.tfstate`. It is configured for `us-east-1` and AWS account `390847857761`. Both roles need access to the adjacent `pixelpushr/production.tfstate.tflock` object for locking. The plan role reads state and the deploy role also writes it. For local formatting and validation without AWS access, use `terraform -chdir=tf fmt -check -recursive`, `terraform -chdir=tf init -backend=false`, and `terraform -chdir=tf validate`.

### GitHub Actions

Pull requests and pushes to `main` run lint, type checking, production builds, Lambda packaging, Terraform validation, and all three test suites. A same-repository PR also runs Terraform plan using the `pixelpushr-github-plan` OIDC role with read-only infrastructure and state permissions. Its trust policy uses the repository's `pull_request` subject. Fork PRs run the verification job without AWS credentials.

A passing push to `main` deploys through the GitHub `production` environment using the `pixelpushr-github-deploy` OIDC role. Its trust policy uses the repository's `environment:production` subject. Restrict the environment to `main`. The deploy job creates and applies a fresh plan, runs the migration Lambda, publishes the SPA, invalidates the CloudFront HTML entry, and checks the site and API health endpoints. The operator still needs to complete the browser walkthrough for the first deployment.

### Manual deployment

1. Run `bun install`, `bun run build`, and `bash scripts/package-lambda.sh` at the repository root. The script downloads the AWS RDS CA bundle and packages it in `artifacts/lambda.zip` with the API, migration, and cleanup handlers and the migration files.
2. Authenticate to the target AWS account and confirm the state bucket, domain prerequisites, and initial owner mailbox.
3. Run `terraform -chdir=tf init`, `terraform -chdir=tf validate`, and `terraform -chdir=tf plan -out=release.tfplan`. Review the plan, then run `terraform -chdir=tf apply release.tfplan` when you intend to provision resources.
4. Apply database migrations before first use: `aws lambda invoke --region YOUR_REGION --function-name "$(terraform -chdir=tf output -raw migration_lambda_name)" /tmp/pixelpushr-migration-result.json`, then inspect that response and the migration Lambda logs for `{ "migrated": true }`. Re-run this migration function after every release that adds a migration.
5. Upload the built SPA: `aws s3 sync apps/web/dist "s3://$(terraform -chdir=tf output -raw web_bucket)" --delete`. `--delete` only removes stale build files from this exact web bucket; do not use it with the media bucket. Invalidate the CloudFront HTML entry (or wait for its 60-second cache TTL) before testing the new release. The `/assets/` build files are content-hashed.
6. Check `$(terraform -chdir=tf output -raw api_health_url)` for HTTP 200. Open the web URL output, confirm the owner account, create the organization, invite an admin, and walk through the browser-window display test above.

The Lambda handlers obtain the RDS-managed password from Secrets Manager at cold start. Startup fails clearly if required configuration is missing. `/api/health` returns HTTP 503 if PostgreSQL is unavailable. Request and dependency failures are logged as structured JSON in CloudWatch. API responses are not cached by CloudFront; media is cached for up to a day. The public player URL contains a random display token. Player access control and private media delivery are intentionally out of scope for this MVP; do not upload sensitive material.
